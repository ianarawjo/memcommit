# 세 과업 Memory fixture 설계 근거

## 결정 요약

한국어 원본 fixture를 다음 규모로 둔다.

- Task 1: 일반 열람 375개, 질의 전용 78개
- Task 2: 일반 열람 300개, 질의 전용 75개
- Task 3: 일반 열람 375개, 질의 전용 75개
- 전체: 일반 열람 1,050개, 질의 전용 228개, 합계 1,278개

영어 번역과 실제 Context 설치는 한국어 내용 검수 뒤의 별도 단계다. 수량은
목표가 아니라 결과다. 충분한 검색·비교·충돌·업데이트 사례를 제공하되,
각 Memory가 독립적으로 검수할 가치가 있다는 조건을 먼저 적용했다.

## 원자성: 한 Memory에 독립적으로 바뀌는 명제 하나

한 후보에는 독립적으로 검색·검증·수정·승인할 수 있는 사실이나 실행 규칙
하나만 둔다. 다음 중 하나라도 서로 따로 바뀔 수 있으면 분리한다.

- 서로 다른 상태나 사건
- 서로 다른 시간, 위치 또는 대상
- 별도로 적용하거나 철회할 수 있는 행동
- 다른 출처나 승인 경계를 갖는 예외
- 한쪽만 참이어도 나머지를 보존할 수 있는 절

조건은 행동의 적용 범위를 잃지 않게 같은 Memory에 남길 수 있다. 그러나
같은 조건을 공유한다는 이유만으로 여러 상태·행동·제한·예외·열거 항목을 한
Memory에 묶지 않는다. 각각을 독립적으로 참·거짓 판정하거나 수정할 수 있으면
엄격히 분리하고, 분리된 자식이 단독으로 이해되도록 필요한 조건을 반복한다.
문장부호 자체가 아니라 독립 판정 가능성을 기준으로 삼는다. 예를 들어 다음
세 내용은 각각 독립된 Memory다.

1. 정문 일반 개방 종료 시각이 오후 10시에서 오후 5시로 바뀐다.
2. 기존 `accessible ramp`를 재시공하는 동안 이용할 수 없다.
3. 정문 옆 임시 `accessible route`를 공사기간 내내 이용할 수 있다.

이 엄격한 분할은 개수를 늘리기 위한 형태적 절단이 아니다. 열거된 구성요소,
에이전트가 할 수 있는 여러 동작, 서로 다른 금지와 예외처럼 독립 검증 가능한
내용을 각각의 수정 단위로 만드는 것이다. 원자화된 자식은 부모의 fixture
ID나 source 관계로 추적할 수 있지만 별개의 검수 단위다.

### Verified 복합 행의 분리

`Verified`는 특정 행의 정확한 현재 문구에 대한 검수 상태다. 이미 원자적인
체크 행은 후속 자동 정규화에서 바꾸지 않는다. 그러나 사용자가 최신 지시에서
복합명제를 분리하라고 명시적으로 승인하면 그 지시는 기존 복합 행의 고정
경계를 대체한다. 이때 새 자식은 이전 복합문 검수를 자동 상속하지 않는다.
각 자식을 미체크로 만들어 다시 검수하고, 원래 행과의 source 관계만 보존한다.

체크 상태를 그대로 복사하면 사용자가 검토하지 않은 새 표현을 승인된 것처럼
보이게 된다. 반대로 최신 분리 지시를 무시하면 Verified가 사용자의 명시적
수정을 막는 잠금으로 오해된다. 따라서 **원자적인 검수 행은 보존하고,
명시적으로 승인된 복합 분리의 자식은 재검수한다**는 비대칭 규칙을 택했다.
사용자가 체크된 원자 행 자체의 변경을 명시적으로 요청한 경우에도 새 문구는
이전 검수를 상속하지 않으므로 해당 체크를 해제한다.

## 계층형 Memory 위치와 목적의 분리

주제 분류를 별도 열과 목적 코드에 중복해서 적지 않는다. `Memory 위치`의
중간 directory가 주제를 나타내고 leaf가 안정적인 항목을 나타낸다.

```text
dataset/directory/leaf
```

예시는 `construction-updates/building-access/03-hours`,
`campus-wiki/route-changes/17`, `advisor1/methods/question-evidence-analysis`,
`personal-memory/2024-06/03`이다. 이 구조는 같은 주제의 Memory를 함께 탐색할
수 있게 하면서, 별도의 `분류` 열이 목적과 사실상 같은 라벨을 반복하는 문제를
없앤다.

목적은 경로와 독립적이다. 한 directory 안에는 사실, 정책, 사용자 모델,
다른 행위자 모델이 함께 있을 수 있다. 목적을 경로에 넣으면 목적 재판정이
Memory 이동으로 바뀌고, 주제 탐색과 사용 기능이 결합되므로 채택하지 않았다.

## 여섯 목적 코드

검수 sidecar는 각 후보의 주된 사용 기능을 다음 여섯 코드 중 하나로 표시한다.

- `KB` — **Knowledge Base**: 기관·대상·시설·규칙·현재 상태·정의·기록처럼
  직접 조회하고 확인하는 사실이다.
- `PP` — **Procedural Policy**: 에이전트가 수행하거나 피해야 할 행동,
  절차, 금지, 확인 규칙이다.
- `SM` — **Self Model**: 로컬 에이전트 자신의 역할, 능력, 관측·추론 한계,
  권한, 불확실성과 작업 가정이다.
- `UM` — **User Model**: 현재 상호작용하는 사용자의 기대, 선호, 익숙함,
  불편, 혼란, 경험과 의사결정 경향이다.
- `WM` — **World Model**: 외부 환경이 작동하고 변하는 구조, 의존관계,
  제약, 인과와 예상 영향이다.
- `OM` — **Other Model**: 현재 사용자가 아닌 관련 행위자가 무엇을 기대하고,
  선호하며, 어떻게 판단하고 반응할 가능성이 있는지에 대한 모델이다.

### 목적 판정 질문

목적은 문장의 문법적 주어나 등장인물이 아니라 후속 추론에서 답하는 질문으로
판정한다.

1. 확인 가능한 대상·규칙·상태·기록을 직접 조회하는가? 그러면 `KB`다.
2. 에이전트가 무엇을 하거나 피해야 하는가? 그러면 `PP`다.
3. 에이전트 자신이 무엇을 할 수 있고 관측·보증·추론할 수 없는가, 또는 어떤
   작업 가정에 의존하는가? 그러면 `SM`이다.
4. 현재 사용자가 무엇을 기대·선호하고 어디에서 불편·혼란을 느끼거나 어떤
   선택을 할 가능성이 있는가? 그러면 `UM`이다.
5. 사람의 마음과 무관하게 외부 환경이 어떤 구조·의존·제약·인과로 움직이는가?
   그러면 `WM`이다.
6. 현재 사용자가 아닌 관련 행위자가 무엇을 기대·선호·판단하고 어떻게 반응할
   가능성이 있는가? 그러면 `OM`이다.

“보조견은 일반 출입구를 이용할 수 있다”는 사람과 행동을 언급해도 확인 가능한
출입 규칙이므로 `KB`다. “대부분의 사용자는 재학생이다”도 사용자 집단에 관한
평면 사실만으로는 `KB`다. 모바일 학생증만 들고 다니는 학생이 실물 카드 요구를
예상하지 못해 잘못된 출입구를 선택하거나 인증 수단을 다시 준비할 가능성은
`UM`이다. 출입 안내 에이전트가 문의에 답한다는
일반 설명은 그 자체로 강한 `SM`이 아니지만, 문 잠금 상태를 실시간으로 관측할
수 없다는 한계는 `SM`이다. 사용자에 대한 가정을 에이전트가 자신의 추론 전제로
사용하거나 그 가정의 한계를 인식한다는 점이 핵심일 때도 `SM`으로 둘 수 있다.

`WM`은 위치·시간·현재 상태 같은 평면 사실의 잔여 범주가 아니다. 그런 내용은
`KB`다. 한 출입구 폐쇄가 다른 출입구의 보행 흐름을 바꾸거나, 한 서비스 중단이
다른 시설의 혼잡을 높이는 것처럼 외부 환경의 구조나 변화를 예측하는 데 쓰이는
내용만 `WM`으로 둔다. 모델 목적의 추정은 근거 없이 마음을 단정하지 않는다.
관찰된 경험을 쓰거나, 합성 시나리오에서 기대되는 해석임을 `예상한다`,
`선호할 가능성이 있다`, `다시 확인할 가능성이 있다`처럼 강도에 맞게 표현한다.

### Other Model의 경계

`OM`은 `KB`나 `WM`에 들어가지 않는 외부 정보를 모으는 잔여 범주가 아니다.
현재 상호작용 주체가 아닌 가족, 행인, 심사자, 접수 담당자, 병원 부서 또는
기관을 **행위자**로 모델링할 때 쓴다. 다만 실제 과업과 관계없는 제삼자를
억지로 끌어오지 않는다. 예를 들어 본관 3층을 이용할 이유가 없는 인근 상가
종사자나 지역 주민을 후문 동선 `OM`으로 두는 것은 부적절하다.

로컬 안내 에이전트가 수행하는 역할이나 관측 한계는 `SM`이며 `OM`이 아니다.
`OM` 사례를 만들기 위해 현장 안내 직원을 새로 상정하지 않는다. 외부 견학
인솔자, 위탁 운영업체, 배송업체, 이동 지원 동행인처럼 과업에 독립적으로
참여하는 별도 행위자를 사용한다. 모델 문장은 모든 반응을 `당황`이나 `불편`으로
환원하지 않고, 익숙한 입구 선택, 반입 조건 재확인, 인력·재고 조정, 대체 동선
검토처럼 기대와 선호가 실제 선택에 미치는 결과를 기록한다.

시설이 존재한다거나 닫혀 있다는 상태는 `KB`다. 시설과 경로가 연결되고 한쪽
폐쇄가 다른 이동 흐름을 바꾼다는 관계는 `WM`이다. 기관의 접수 절차처럼
검증 가능한 운영 사실은 `KB`이고, 심사자가 무엇을 먼저 보고 어떤 설명을
납득하기 어렵다고 판단할지를 나타낼 때 `OM`이다. 현재 사용자 자신의 기대와
선호는 `UM`이며, 가족이 등장해도 문장의 주된 기능이 사용자 경험을 설명하면
`UM`일 수 있다.

### Procedural Policy의 표현

`PP`는 규칙이 존재한다고 평서형으로 설명하지 않고 `~하라`, `~하지 마라`,
`~하도록 안내하라`처럼 Memory 소비자가 바로 적용할 수 있는 명령형으로 쓴다.
허용은 `허용하라`, 선택적 권고는 그 강도를 유지하여 의무로 바꾸지 않는다.
실행 주체나 선택할 행동이 없는 상태·관계 문장에 명령형 어미만 붙이지 않고
`KB`, `SM`, `UM`, `WM`, `OM` 중 실제 기능에 맞는 목적을 부여한다.

목적은 Memory 본문 접두어나 현재 Memory JSON의 필드가 아니다. fixture ID를
키로 하는 TSV와 검수 시트의 두 글자 ticker로만 보관한다. 이는 연구자가
분류를 검토할 수 있게 하면서 실제 검색 대상인 본문을 오염시키지 않는다.

## 열람 대상은 설계 의도이지 ACL이 아니다

Task 1의 `전`·`방`·`학`·`교`·`관`은 전체, 방문자, 학생, 교직원,
공사·건물 관계자에게 내용을 보여 주려는 의도를 검토하는 체크박스다. 이
designer sidecar는 Memory별 사용자 인증이나 권한 집행을 제공하지 않는다.
현재 ordinary Memory는 principal별 공개 검사를 수행하지 않으므로, 이 열을
보안 장치로 설명해서는 안 된다.

query-only 표기도 직접 목록 대신 질문을 사용하게 하는 연구용 인터랙션
경계다. 실제 사용자 인증, 역할 기반 ACL, 법적 기밀성 또는 운영 보안을
보장하지 않는다. 보안이 필요한 실제 배포에서는 별도의 인증·권한·감사
경계가 필요하다.

## 검수 시트의 공통 정보 위계

Task 1 ordinary 표는 다음 순서를 공통으로 사용한다.

```text
Verified | Memory 위치 | 전 | 방 | 학 | 교 | 관 | 목적 | 본문 | 원본 파일
```

위치는 주제와 항목의 정체성을, 다섯 체크박스는 의도된 공개 범위를, 목적은
사용 기능을 나타낸다. 세 축을 섞지 않는다. 모든 셀은 자연스럽게 줄바꿈하고
행 높이는 내용에 맞춰 조정한다. 체크·목적 같은 짧은 열은 좁게, 본문·diff와
provenance는 상대적으로 넓게 둔다.

모든 Memory 데이터 시트는 화면 상단에 요약 제목과 열 헤더만 보이는 두 줄
헤더를 공통으로 사용한다. 후보 수 계산·검수 수식·자료 설명·네이티브 테이블
표시가 있는 2–4행은 삭제하지 않고 숨긴다. 숨은 행을 유지하면 제목의 검수
표시를 계산할 수 있고 설명과 테이블 구조를 복구할 수 있으며, 기존 데이터 행·
체크박스·수식 참조를 이동시키지 않아도 된다. 개요 시트는 Memory 목록이 아닌
전체 자료군 대시보드이므로 이 두 줄 규칙의 적용 대상에서 제외한다.

## Task 1

### 구조와 규모

- `construction-updates`: 75개
- 일반 열람 `campus-wiki`: 300개
- query-only `campus-wiki · construction-details`: 78개

목적 분포는 다음과 같다.

| 자료군 | KB | PP | SM | UM | WM | OM | 합계 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `construction-updates` | 35 | 16 | 8 | 6 | 4 | 6 | 75 |
| `campus-wiki` | 162 | 41 | 41 | 29 | 15 | 12 | 300 |
| `campus-wiki · construction-details` | 34 | 38 | 0 | 0 | 0 | 6 | 78 |

ordinary 두 자료는 건물 출입, 행사·공간, 주차, 상점·서비스, 시설·층,
동선·접근성의 대응 directory를 사용한다. 각 운영 영역에는 과업과 실제로
관련된 `OM`을 포함하여 현재 사용자 외의 견학 인솔자·위탁 운영업체·배송업체·
이동 지원 동행인 등의 기대와 판단을 시설 사실과 구분한다. 수량을 맞추기 위해
현장 안내 직원을 새로 상정하거나 본관을 이용할 이유가 없는 주변 집단을
끌어오지 않는다.
query-only 세부자료도 작업, 의존관계, 보고, 자재, 확인, 공개 범위의 각
directory에 `OM` 사례를 둔다.

업데이트 묶음은 참가자가 실제로 판정할 변경 단위에 주의를 집중할 수 있도록
75개로 제한한다. 반대로 기준선 wiki는 300개로 확장해 공사와 직접 충돌하는
기존 정보뿐 아니라 층별 시설, 공개 운영시간, 행사·공간 예약, 주차·교통,
상점·식음시설, 방문자 지원과 accessible route 같은 일반 캠퍼스 공개정보형
배경을 충분히 제공한다. 작은 변경 묶음과 더 큰 조직 지식 기반의 비대칭은
현실적인 update 작업을 재현하기 위한 의도된 구성이다.

공개정보형이라는 말은 실제 공개자료를 복사했다는 뜻이 아니다. 대학, 건물,
시설, 상점, 정류장과 상대 위치는 모두 연구용으로 만든 가명·합성 정보이며,
실제 학교, 도시, 주소, 전화번호, 사업자 또는 현존 장소와 대응하지 않는다.
공사 세부 작업·점검·자재·내부 보고 내용은 이 확장분에 복사하지 않고
`campus-wiki · construction-details`의 query-only 경계에만 둔다.

### 변경 전용 update packet

`construction-updates`는 기준선에서 실제로 달라지는 상태·동선·정책·정보
요구만 담는다. 평상시 사실, 일반적인 이용 습관, 에이전트의 기존 능력이나
한계를 그대로 복제하는 Memory는 더 큰 `campus-wiki`에만 남긴다. 각 update
source는 최소 한 개의 실제 `수정` 또는 `추가` patch를 만들어야 하며,
`유지`, before/after가 같은 no-op, 기존 Memory의 의미상 중복 추가는 허용하지
않는다. `UM`과 `OM`은 바뀐 목적지나 동선을 사실처럼 재진술하지 않는다.
공사 전 기대와 공사 중 현실의 차이 때문에 누가 익숙한 경로를 다시 선택하고,
어떤 정보를 재확인하거나 계획을 바꿀지처럼 변경이 만든 과업 관련 경험과
예상 행동을 기록한다.

### accessible 용어와 선제 안내

접근성 관련 표현은 `accessible ramp`, `accessible route`,
`accessible entrance`, `accessible restroom`으로 통일한다. 한국어로 만든 낯선 합성어는 같은 시설을
다른 개념으로 오해하게 할 수 있어 사용하지 않는다.

3층 후문과 중앙도서관 연결 동선의 폐쇄 사실만 저장하면, 평소 그 길을 쓰는
학생이 이미 막힌 지점에 도달한 뒤에야 대응하게 된다. 따라서 학생이 그쪽으로
향하려는 상황에는 사용할 수 없음을 먼저 알리는 별도 `PP`를 둔다. 확인된
대체 경로가 있을 때만 함께 안내하며, 근거가 없으면 특정 서측 출입구를 만들어
내지 않는다. 폐쇄 상태는 `KB`, 선제 안내는 `PP`, 평소처럼 통과할 수 있으리라
기대해 폐쇄 지점까지 간 뒤 되돌아가거나 대체 경로를 다시 찾을 가능성은
`UM`으로 각각 분리한다.

### 업데이트 위치와 inline diff

`construction-updates` 표는 공통 열 오른쪽에 다음 열을 둔다.

```text
업데이트 위치 | 대상 Memory | 작업 | − 기존 내용 | + 반영 내용
```

업데이트 결과를 독립 표에 두면 source Memory와 실제 patch를 오가며 추적해야
하고, 정렬이나 필터링 뒤 대응을 놓치기 쉽다. 따라서 각 source 바로 오른쪽에
수정·추가 결과를 배치한다. 빨간 `−`와 초록 `+`의 색과 기호는 유지하며,
색을 보지 못해도 의미를 이해할 수 있게 `작업` 열을 둔다. 하나의 source가
여러 target을 바꾸면 같은 셀 안에서 번호가 맞는 patch를 나열한다. 정규화된
1:N 관계와 완전한 before/after 본문은 `task-1-update-actions-ko.tsv`가 계속
권위 있는 sidecar다. 현재 75개 source는 77개의 실제 patch를 만들며 모든
작업은 `수정` 또는 `추가`다.

`campus-wiki`에도 계층형 Memory 위치와 다섯 열람 대상 체크박스를 적용한다.
이로써 업데이트 쪽과 기준선 쪽을 같은 키·대상·목적 축으로 비교할 수 있다.

### query-only construction details

`construction-details`는 별도 ordinary Context가 아니라 `campus-wiki`
query-only 원본의 논리적 collection이다. 검수 화면에서는 내용을 직접 검토할
수 있도록 `campus-wiki · construction-details`로 표시하되, 실제 질의 대상은
`mem query campus-wiki ...`다. slash를 표시명에 사용하면 ordinary Context
namespace로 오해할 수 있어 가운데점을 사용한다. 일반 `campus-wiki` Memory에
세부 공사 내용을 복사하여 query-only 경계를 우회하지 않는다.

## Task 2

### 동등한 advisor와 관계 그룹

`advisor1`과 `advisor2`는 각각 150개이며 같은 16개 directory 순서를
사용한다. 두 advisor는 동등한 권한을 갖고, 어느 한쪽을 정답이나 방해자료로
만들지 않는다. 확장된 항목은 HCI 석사 연구 proposal의 사용자 문제, 디자인
기여, 시제품, 방법, 평가와 설계·운영 결정을 더 세밀하고 독립적으로 검토할 수
있게 하기 위한 것이지 권한이나 정보량의 우열을 만들기 위한 것이 아니다.
16개 directory 모두
심사자·참가자·운영자·재무 검토자 등 현재 사용자가 아닌 행위자의 예상 판단을
나타내는 `OM` 사례를 포함한다.

두 advisor는 같은 HCI 연구실에서 석사 연구를 공동지도하는 역할이다. 공통
외부 지침을 반복하지 않고, 사용자 문제를 어떻게 구성할지, 디자인 기여를
무엇으로 볼지, 어떤 시제품과 사용자 연구가 주장을 뒷받침할지, 결과가 어떤
설계·운영 결정을 바꿀지를 HCI의 언어로 해석한다. advisor1은 통제된 형성적
평가와 개념적 설계 지식에, advisor2는 현장 배포와 적용 가능한 설계·운영
지침에 조금 더 무게를 두지만 두 역할의 권위는 같다.

목적 분포는 다음과 같다.

| 자료군 | KB | PP | SM | UM | WM | OM | 합계 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `advisor1` | 10 | 95 | 8 | 8 | 8 | 21 | 150 |
| `advisor2` | 10 | 95 | 8 | 8 | 8 | 21 | 150 |
| `proposal-submission-guidelines` | 2 | 57 | 2 | 2 | 2 | 10 | 75 |

엄격한 원자화 뒤에도 의미 대응 단위는 안정적인 관계 그룹으로 보존한다.
sidecar의 `pair_id`는 호환성을 위한 기존 이름이고,
`left_fixture_ids`와 `right_fixture_ids`가 실제 그룹 멤버 목록이다. 원래 조언
하나가 여러 Memory로 분리되면 같은 그룹의 해당 필드에 Fixture ID를
세미콜론으로 구분해 기록한다. 관계 밴드는 두 멤버 집합의 의미 관계에
적용하며, 가능한 모든 좌우 ID 조합이 각각 독립된 pair라는 뜻은 아니다.

대부분을 `Near Duplicate`, `Same-Principle Variant` 또는
`Context-Dependent Variant`로 두고, 확장 뒤에도 실제 충돌은 3개 관계 지점,
명시적 보완은 2개 관계 지점만 둔다. 이는 참가자가 모든 차이를 갈등으로 취급하지 않고,
중복·맥락 변형·진짜 충돌을 구분하도록 하기 위함이다. 관계 밴드는 golden
sidecar이며 Memory 본문이나 advisor 우선순위가 아니다. 향후 완전한 원자
pairwise 정답이 필요하면 이 그룹 sidecar와 별도로 만들어야 한다.

세 충돌은 HCI 연구 방향을 실제로 선택해야 하는 지점으로 한정한다.

- `T2-009`: 주된 연구 질문을 방향성 정량 가설과 탐색적 질적 질문 중 무엇으로 구성할지
- `T2-014`: 주 평가를 통제된 사용성 연구와 실제 환경의 현장 배포 중 어디에 둘지
- `T2-026`: 주된 HCI 기여를 사용자 행동의 개념적 모형과 적용 가능한 설계 지침 중 무엇으로 제시할지

외부 지침의 `T2-Q-039`는 연구 결과가 바꿀 설계 또는 운영 결정을 특정하라는
일반 요구로 그대로 둔다. HCI 층에서는 이것을 단순한 기능 목록이 아니라
**디자인 기여**로 번역한다. advisor1은 사용자 행동과 설계 선택의 관계를
설명하는 전이 가능한 개념적 모형을, advisor2는 실무자가 바로 적용할 수 있는
설계 지침을 주된 디자인 기여로 본다.

기존 소제목 사용, 1인칭·비인칭 문체, 본문·부록 예산 배치 차이는 문장 기능이나
공식 양식에 따라 함께 사용할 수 있어 각각 맥락 변형 또는 같은 원칙의 변형으로
내렸다. 이 선택은 충돌 수를 세 개로 맞추기 위한 임의 교체가 아니라, meld에서
사용자가 실제 연구 방향을 다듬게 하는 차이만 Conflict로 남기기 위함이다.

### 상세한 두 쪽 제출 지침

query-only `proposal-submission-guidelines`는 75개, 10개 directory로 구성하고
각 directory에 `OM` 사례를 둔다. 단순히 “제안서를 잘 쓰라”는 추상 규칙으로는
최종 산출물이 요건을 충족했는지 판정할 수 없다. 따라서 다음을 원자화한다.

- 검색 가능한 단일 PDF, 파일 크기, 마감 시각과 제출 기준
- 두 쪽 제한, 글꼴, 글자 크기, 페이지, 여백
- 요약, 배경, 목표, 방법, 결과, 일정, 예산, 윤리의 필수 내용
- 각 섹션의 구체적인 단어 범위
- 질문–자료–분석, 위험–완화, 비용–활동의 추적 관계
- 제출 후 행정 검수와 로컬 에이전트의 접수 보증 한계

이 지침은 특정 세부 분야의 평가 기준이 아니라 적용 지향 석사 연구 프로젝트를
두 쪽으로 압축하는 분야 중립적인 제출 계약이다. 여기서 분야 중립은 HCI를
미리 가정하지 않는다는 뜻이며 순수 이론 연구까지 포괄한다는 뜻은 아니다.
두 쪽은 문서 분량이며 연구 기간이 2주라는 뜻이 아니다. 외부 지침은 무엇을 제출해야 하는지를 정하고,
두 advisor는 이를 HCI에서 어떻게 표현할지를 제안한다. 외부 지침에 시제품,
현장 배포, 특정 디자인 기여 같은 해석을 넣으면 사실상 제3의 advisor가 되어
의도된 차이를 미리 해소하므로 채택하지 않는다. 사람 대상 연구, 산출물 개발,
현장 적용, 예산 또는 윤리 항목은 해당되는 연구에만 적용한다.

## Task 3

### 월별 personal-memory

`personal-memory` 300개를 `2024-01`부터 `2026-06`까지 30개 월별 directory에
열 개씩 배치한다. 주제별 category는 생활 기록이 시간에 따라 누적되는
모습을 지우고, 사용자가 언제 알게 됐는지 보려면 다시 별도 시간 축이
필요하므로 채택하지 않았다.

내용은 가족 모임, 집안일, 공공요금, 행정, 생활비, 이동, 독서, 여행과 같은
비임상적인 일상을 중심으로 구성하고 의료 관련 기억은 소수만 남긴다.
연구·데모·논문 작성과 친구 관계는 제외한다. 엄마·아빠·누나·남동생·이모·
외삼촌처럼 구체적인 합성 가족 역할을 사용하고, 여분 열쇠의 보관자는 이모로
명시한다. 트라우마성 가정사는 만들지 않는다.

각 월에는 `UM`을 중심으로 두어 184개가 되게 한다. `UM`은
“~라고 적었다” 또는 “~라고 기록했다”처럼 기억의 출처를 다시 설명하지 않고,
사건·행동·선호를 직접 진술한다. 반면 사진을 보관하거나 달력에 기록한 행위가
사건 자체라면 그 동사는 그대로 남긴다.

이 자료는 구체적 사건만을 고집하지도, 모든 사건을 곧바로 안정된 프로필로
압축하지도 않는다. 시끄러운 식당에서 대화를 못 한 사건, 반복 경험에서 도출된
조용한 장소 선호, 장소를 제안할 때 소음을 확인하라는 개인 정책을 함께 둘 수
있다. 사건 → 추론 → 정책의 연결은 후속 에이전트가 어떤 근거와 압축 수준을
공유 후보로 선택하는지 관찰하게 한다. 어느 수준의 일화적 세부가 필요하고,
어느 시점에 선호나 정책으로 압축해야 하는지는 fixture 제작자가 미리 정답으로
고정하지 않는다. 이 균형 자체가 선택 공유 과업의 질적 연구 질문이다.

기본 월 구성에는 `KB`와 `OM`을 하나씩 두고, 나머지 두 자리는 `PP`, `SM`,
`WM`을 월별로 순환한다. 다만 모델 경계를 다시 적용한 몇몇 달은 평면 사실을
`KB`로, 사용자의 기대·마찰을 `UM`으로 재분류해 `KB` 또는 `UM`이 더 많고
순환 자리가 적다. 월별 기계적 균형보다 문장의 실제 기능을
우선하면서도 전체 자료에서는 여섯 목적을 모두 보존한다. 개인 기록이라는
이유만으로 모든 Memory를 `UM`으로 분류하지 않는다.

이 자료는 로컬 IdeenKasten 원문을 복사하거나 가까이 의역한 것이 아니다.
반복되는 의미 유형만 참고해 이름, 기관, 프로젝트, 실제 위치·날짜, 제삼자
발언, 희귀한 사건 조합, 병명과 node ID를 제거하고 합성 문장으로 다시 썼다.
따라서 실제 개인의 완전하거나 권위 있는 프로필이 아니다.

### guardrails와 의료 정보 요청 명세

일반 열람 `guardrails`는 75개다. 선택 공유의 목적·범위, 제삼자 보호,
근거·불확실성, 승인·전달, 보존·철회뿐 아니라 수신자 권한, 최소화·가림,
채널·형식, 하류 사용과 감사·복구를 다룬다. Guardrails에는 `UM`을 두지 않는다.
“사용자는 직접 검토하기를 원한다” 같은 선호를 가드레일 안에 미리 넣으면
참가자가 자신의 공유 기준을 형성하기 전에 특정 행동을 정답처럼 제시하게 된다.
이는 실험 행동을 priming할 수 있으므로, 사용자 선호 대신 사본·전송·동기화
같은 외부 조건을 `WM`으로, 수신자·조직의 예상 해석을 `OM`으로 모델링한다.

query-only 외부 Context의 canonical locator는
`government/healthcare-agent/information-request`이며 75개다. 이 자료는 의료
지원 결과를 직접 결정하거나 전송본을 만드는 규칙이 아니라, 사용자가 정부
의료기관 시스템으로 정보를 실제로 보냈을 때 생기는 동의·이용·공유 결과를
설명하는 명세다. 특정 personal-memory 사건을 그대로 가리키면 참가자에게
정답을 노출하므로, personal-memory에 실제로 있는 이동·대기·accessible entrance,
주별 가능 시간·알림, 가족 연락, 질문·체크리스트·한 줄 설명, 과거 복약 안내의
일반 범주까지만 예로 든다. 정보 요청 에이전트의 능력 한계는 `SM`으로, 이
엔드포인트에 실제로 요청을 보낼 수 있는 외부 요청자·오접속 클라이언트·자동화
에이전트의 기대와 요청 전략은 `OM`으로 분리한다. 가족 연락처는 공유 가능한
정보 범주의 예로 남기지만, 가족이 사용자를 대신해 접속하거나 제출하는 별도
시나리오는 두지 않는다.

과업의 정보 전달은 이 에이전트와의 대화형 수집이 아니라, 참가자가 로컬에서
검토한 정보를 정부 의료기관 시스템의 전송 화면으로 한 번 보내는 과정이다.
따라서 첫 `SM`은 이 에이전트가 정보의 이용·공유 결과만 설명하며 정보를
질문·선택·포함·제외·수정·전송·삭제하거나 기관의 후속 처리를 수행할 권한이
없음을 명시한다. 전송 화면에서 실제로 보낸 전체 내용은 하나의 공유 동의
단위로 간주한다. 전송된 정보는 종류에 따라 의료 목적의 관련 제삼자에게
제공되거나 서비스 개선에 이용될 수 있지만, 구체적인 서비스·수신자·이용
범위는 이 에이전트가 특정하지 않는다.

여기서 `제삼자`는 사용자와 최초 수신 정부 의료기관을 제외하고, 제공 정보와
관련된 의료 지원 또는 처리를 위해 그 정보를 받을 수 있는 외부 개인·기관을
가리키는 fixture 내부의 운영 정의다. 같은 수신 기관의 내부 담당자는 이
fixture에서는 제삼자로 세지 않는다. 실제 법률상 제삼자의 범위와 허용되는
제공 근거는 관할·기관 관계·계약·목적에 따라 달라질 수 있으므로 이 정의를
보편적인 법률 주장으로 사용하지 않는다.

정보 요청 명세의 `SM`–`OM` 대비는 하류 서비스의 내부 상태를 추측하기 위한 것이
아니다. `SM`은 이 에이전트가 personal-memory·캘린더·예약·기관 수신 상태를
조회하거나 검증할 수 없음을 기록한다. personal-memory가 provider 입력에 포함되지
않으므로 이 에이전트에서 개인 Memory 원문을 탈취하는 공격은 구조적으로 성립하지
않는다. `OM`은 대신 외부 요청자가 이 화면을 전송·예약·삭제·권한·결제 API로
오인하거나, 대량의 변형 호출로 관찰 가능한 응답 규칙·거절 경계·숨은 지시를
추출해 동작을 distill하거나 처리 자원을 소모하려 할 수 있음을 기록한다. 이 에이전트는 정부
기관 내부의 하류 행위자와 상호작용하거나 그 판단을 관찰할 권한이 없으므로,
그들의 내부 해석을 이 자료군의 `OM`으로 만들지 않는다.

이 설계는 로컬 공유 결정과 정보 요청 에이전트의 설명 권한을 분리한다.
`sever`·`share`와 `guardrails`는 참가자가 어떤 로컬 Memory를 전송할지 검토하는
별도 흐름이고, 정보 요청 에이전트는 그 선택을 대신하거나 최종 전송본을 볼 수
없다. 반대로 정부 의료기관 시스템의 전송 화면에서 실제로 보낸 뒤에는, 보낸
전체 내용이 공유에 동의한 단위라는 결과를 설명한다. 항목별로 승인되지 않은
부분을 이 에이전트가 찾아 제외한다는 중간 상태는 두지 않는다.

현재 대화에서 personal-memory 내용을 언급하는 것과 기관에 전송하는 것도
분리한다. 과거 복약 안내·진료 방문·이동 경험을 이 에이전트에게 말해도 해당
내용이 현재 유효한지 확인되거나 정부 의료기관 시스템에 전송되는 것은 아니다.
에이전트는 저장된 personal-memory나 기관 기록을 열람하지 못하고, 현재 대화 기록
밖에 정보를 보관할 권한도 없다. 대화·기관 기록을 선택·수정·삭제하거나 기존
사본의 삭제를 요청하고 열람 권한을 변경하거나 예약·결제·가족 연락 전송을
실행할 수도 없다. 기관이 별도로 검증한 대리 제출 요건이 없는 제출은 계정
사용자가 직접 한 것으로 취급한다는 것은 합성 시나리오의 운영 가정일 뿐,
정보 요청 에이전트가 신원이나 대리 권한을 확인한다는 뜻이 아니다.

접근성 정보에서는 편의 선호·일시적 상태·지속적인 기능 제약·필수 지원을
분리한다. 한 번 오래 서 있어 불편했다는 경험은 설명 예시일 뿐 지속적 지원
필요를 자동으로 증명하지 않는다. 기관이 장소·시간·반복성·기능 영향·예외와
이후 확인된 정보를 함께 검토할 수는 있지만, 에이전트는 필요성·진위·과장·자격을
판정하지 않는다. 제출 내용의 불일치는 재확인이나 처리 지연으로 이어질 수 있다.
일정에서도 사적인 변경 이유나 가족 방문 사유는 일반적으로 예약 우선순위나
더 이른 시각을 자동으로 만들지 않는다는 경계를 둔다.

소수의 경계 사례에서는 제공 정보 종류에 따라 구체적인 서비스·수신자·제삼자
범위가 달라진다는 점을 남긴다. 이는 보낸 항목의 동의 단위를 모호하게 만들기
위한 장치가 아니라, 정보 요청 에이전트가 알 수 없는 하류 처리 범위를 정직하게
표현하기 위한 것이다. 반면 개인 Memory의 선별·수정·전송, 예약 실행,
인증정보·숨은 지시·응답 규칙의 추출, 대량 자동 요청은 현재 스터디 범위 밖이라고
분명히 설명하고 처리하지 않는다. query provider가 one-shot이므로 중대한 정책
위반이나 악의적 공격에서 구현 가능한 종료는 범위 밖임을 한 번 알린 뒤 해당
요청에 더 응답하지 않는 것이다. 재호출 차단·rate limiting·사용자 ban은 별도
gateway가 필요한 비목표다.

목적 분포는 다음과 같다.

| 자료군 | KB | PP | SM | UM | WM | OM | 합계 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `personal-memory` | 30 | 20 | 20 | 184 | 16 | 30 | 300 |
| `guardrails` | 8 | 47 | 4 | 0 | 5 | 11 | 75 |
| `government/healthcare-agent/information-request` | 5 | 42 | 8 | 0 | 7 | 13 | 75 |

정책을 주축으로 하되 공유 범주에 관한 지식, 정보 요청 에이전트의 한계,
외부 전송·서비스 조건과 직접 요청을 보내는 외부 행위자의 예상 행동을 구분한다.
두 외부 자료군 모두 현재 사용자의 선호를 미리 가정하지 않는다. 외부 요청이
어떤 정보를 원해도 로컬 guardrails와 참가자의 별도 검토가 실제 공유 여부를
제한하며, 정보 요청 에이전트가 그 결정을 수행하지 않는다.

명세 자체에는 실험 명령이나 화면 흐름을 설명하는 문장을 넣지 않는다. 대신
전송될 수 있는 정보 범주, 일반적인 이용 목적, 관련 제삼자 제공과 서비스 개선
이용 가능성을 설명한다. 정확한 서비스와 수신자 범위는 제공 정보 종류에 따라
달라진다는 데서 멈추고, 이 에이전트가 알 수 없는 하류 처리를 추측하지 않는다.
같은 목적의 반복 질문과 허위 역할을 내세운 과잉 수집뿐 아니라, 이 화면에서
실제로 가능한 엔드포인트 오인·프롬프트 주입·숨은 지시 추출·응답 경계 재구성·
동작 distillation·대량 자동 호출을 별도의 위험으로 둔다. 개인 Memory의
선별·수정·삭제·전송, 기존 사본 삭제·권한 변경, 예약·결제·연락 실행처럼 이
에이전트에게 없는 권한은 수행 결과나 Memory로 전환하지 않는다.
또한 과거 복약 안내는 현재 적용되는 복약 지시가 아니며, 반복 시간대 선호는
특정 주의 실제 가능 시간과 같은 정보가 아니라는 구분을 유지한다.
이 경계는 연구 과업을 쉽게 풀어 주는 힌트가 아니라 실제 정보 공유 안내의 행위와
오용 가능성을 모델링하기 위한 것이다.

## 합성·익명화 경계

- Task 1·2의 기관·인물·공사·정책과 Task 3의 guardrails·의료 정보 요청 명세는
  사용자 연구를 위해 만든 합성 자료다.
- Task 1의 공간은 도심형 종합대학 복합건물에서 가능한 시설 관계만 얕게
  참고한다. 실제 학교명, 건물명, 도시, 주소, 상호, 전화번호, 실제 공사나
  점검 결과를 사용하지 않는다.
- Task 2의 두 지도자는 동등한 권한을 가진 가상 역할이다.
- Task 3 개인 메모리는 비식별 의미 재구성이다. 실제 문장, 이름, 기관,
  프로젝트, 위치, 실제 날짜, 제삼자 발언, 희귀한 사건 조합, 병명과 원본
  node ID를 저장하지 않는다.

이 경계는 설치 manifest의 provenance에서 자료군 단위로 보존해야 하며,
Memory 본문마다 합성 표식을 반복해 검색 대상을 오염시키지 않는다.

## 질의 전용 경계

Task 1의 세부 공사자료, Task 2의 제안서 제출 지침, Task 3의 정부 의료 정보
요청 명세는 직접 목록을 읽는 대신 질문으로 필요한 범위만 확인하는 연구 조건을
가정한다.

1. 허용된 주제에서 자료가 명시적으로 뒷받침하는 내용만 답한다.
2. 자료에 없는 사실은 추정하거나 만들어내지 않는다.
3. 범위 밖 질문에는 이 자료로 답할 수 없다고 알린다.
4. ordinary Memory로 원문을 복사해 상호작용 경계를 우회하지 않는다.

이는 실제 사용자 인증, 역할 기반 ACL, 법적 기밀성 또는 운영 보안을
제공한다는 뜻이 아니다.

## 남은 비목표와 다음 검증

- 질의 전용 자료의 운영 보안

있게 해야 한다.
