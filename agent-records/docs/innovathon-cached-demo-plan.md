# Innovathon 캐시 응답 데모 계획

- 작성일: 2026-09-30
- 작성 주체: 대화에서 정한 방향을 정리한 에이전트 기록.
- 범위: `memcommit-innovathon` / `innovathon` 브랜치 전용.
- 상태: **계획만 기록. 캐시 재생·초기화 변경·Sync·외부 프로그램 연동은 이 문서에서 구현하지 않는다.**
- 이 문서는 시연 시나리오 계획이며, 구현 완료나 operation route 검토 상태를 뜻하지 않는다.

## 목적과 결정

LLM 응답이 매번 달라져 시연의 쟁점과 수정 결과가 바뀌는 대신, 준비하고 확정한 응답을 캐시에 저장해 재생한다. 화면 출력만 흉내 내는 mock이 아니라, 캐시 응답을 기존 처리 경로에 공급하고 실제 Context 변경·검증·저장·Checkpoint·Receipt를 실행하는 데모를 목표로 한다.

현재 해당 캐시가 이미 마련되어 있거나 실제 모델 호출로 수집되었다고 가정하지 않는다. 캐시를 채우는 작업과 구체적인 내용 확정은 이후에 한다. 배포용 기본 동작을 바꾸는 기능이 아니라 Innovathon 시나리오에 한정한다.

이번에는 계획만 남긴다. 별도의 실행 패키지·캐시 폴더 구조·설정값은 구현할 때 정한다. 앞서 이야기한 `init-study`의 데모 전환도 후속 작업으로 남긴다.

## 시연 순서

```text
외부 프로그램에서 Skill 가져오기
↓
Profile로 Sync
↓
기존 Context와 Merge
↓
정해 둔 쟁점 2개를 Resolve 화면에서 검토
↓
선택 또는 Intent → 그 입력에 대응하는 캐시 변경안
↓
캐시 재검사 결과 → Preview·Apply → 성공
↓
Query → 병합 직후 상태에 맞는 캐시 답변
↓
개인화 Update → 캐시 변경안 → 승인·저장 → 성공
↓
Query → 개인화 이후 상태에 맞는 캐시 답변
↓
결과 확인
↓
다시 Sync
↓
외부 프로그램에서 사내 내부 마켓플레이스로 업로드
```

Sync와 마켓플레이스 연동은 앞으로 만들 별도 기능이다. 이 흐름에 포함했다는 이유로 현재 사용할 수 있다고 표시하지 않는다. 실제 외부 업로드는 이 계획을 기록하는 작업에 포함되지 않는다.

## 준비할 캐시 응답

| 단계 | 저장·재생할 내용 | 기존 구현이 계속 맡을 부분 |
| --- | --- | --- |
| 최초 Audit | 쟁점 2개의 판정·이유·근거 Memory 연결 | 현재 Context와 연결된 Audit 객체 구성·검증 |
| Resolve 제안 | 각 쟁점의 `proposed_direction` | 선택지 구성·선택 화면·사용자 입력 |
| Resolve의 Update 계획 | Suggestion 또는 예정된 Intent에 대응하는 추가·수정·삭제 계획 | `UpdatePlan` 검증·변경 결과 계산·diff |
| 재검사 | 변경 후 상태에 대응하는 고정 검사 응답 | 다음 라운드 필요 여부 판단·선택 이력 반영 |
| 병합 후 Query | 답변 본문·주장별 근거 연결 | 인용·Reference 구성·출력 |
| 개인화 Update | 개인화 입력에 대응하는 변경 계획 | 승인·실제 저장·Checkpoint·Receipt |
| 개인화 후 Query | 개인화된 내용을 반영한 답변과 근거 연결 | 인용·Reference 구성·출력 |

Suggestion 채택(`CONFIRM`)과 사용자 입력(`INTENT`)은 Resolve가 구분한다. 두 경우 모두 쟁점 정보와 근거 원문에 채택한 지침을 붙여 Update에 전달한다. 캐시는 이 입력에 맞는 변경 계획을 반환한다. 같은 입력에는 같은 효과를 재생하되, 서로 다른 선택에 같은 변경을 강제로 적용하지 않는다. KEEP BOTH / KEEP AS IS는 기존의 보존 의미를 유지한다.

재검사 응답을 고정한다는 것은 초기 쟁점을 무조건 반복해서 반환한다는 뜻이 아니다. 계획한 변경 후 상태에는 그 상태에 맞는 응답을 반환한다. 기본 시연은 계획한 결정을 거친 뒤 새로 해결할 쟁점 없이 Preview로 이어진다. 후속 라운드가 필요하면 별도 상태와 응답을 준비한다.

## 연결 방향

1. Resolve·Update·Audit에서 사용하는 제공자와 Query에서 사용하는 제공자의 응답 반환 지점을 데모 캐시로 연결한다. Query는 제공자 연결이 별도이므로 함께 연결해야 한다.
2. 가능한 한 기존 응답 해석·객체 구성 경로를 그대로 사용한다. 최종 `ResolveProposal`이나 Receipt를 나중에 바꿔 끼우지 않는다.
3. 캐시에는 응답 내용과 효과를 고정하고, 현재 입력의 Context·Memory 식별자에 맞게 연결한다. 다른 실행의 UID·digest를 그대로 반환하지 않는다.
4. 기존의 변경안 검증, 선택한 diff와 실행 계획의 일치, 입력 변경 여부·권한 검사, 실제 저장을 유지한다.

현재 연결 후보는 다음과 같다. 이 목록은 구현을 시작할 때 재확인한다.

- Merge → Resolve: `application/operations/merge/resolve_preparation.py`
- Audit 획득: `application/operations/resolve/preparation.py`
- 해결 제안 생성: `application/operations/resolve/resolution_options/generation.py`
- 선택별 Update: `application/operations/resolve/choice_plans.py`
- 변경 결과 재검사: `application/operations/resolve/proposal.py`
- 공통 Update 계획: `application/operations/update/model/planning.py`
- 일반 Query 응답: `application/operations/query/ordinary_application.py`, `answer.py`

## 캐시 선택과 반복 실행

- 시나리오·단계·현재 입력 내용·선택 또는 Intent·질문을 기준으로 대응하는 응답을 선택한다. 정확한 키 형식은 구현 시 정한다.
- Query는 호출 횟수가 아니라 현재 Context 내용으로 병합 직후와 개인화 이후를 구분한다. 같은 상태에서 다시 질문하면 같은 답변과 근거가 나온다.
- 사용자에게 보여줄 문장과 실제 저장 결과가 일치해야 한다. Query의 근거도 그 시점에 존재하는 Memory와 연결한다.
- 지원하는 Intent와 질문을 먼저 정한다. 예정하지 않은 입력에 무관한 응답을 반환하거나 실제 LLM으로 자동 전환하지 않고, 캐시가 없는 입력임을 알린다.
- 초기 상태로 되돌려 시연을 다시 시작하는 방법도 구현 단계에서 마련한다. `init-study`를 활용해 OpenAI Docs 데모 자료만 준비하는 방향이며, 정확한 Context 구성과 초기 선택 위치는 후속 확정 사항이다.

## 대기 표시

화면에 보이는 준비 단계마다 약 2~3초의 시연용 대기를 둔다. 기존 공용 `. → .. → …` 애니메이션을 재사용한다. 이 대기는 실제 LLM 추론 시간이 아니라 캐시 재생 시연을 위한 의도적인 표시 시간이다.

내부 함수 호출마다 중복 대기를 누적하지 않고, 사용자에게 보이는 단계 단위로 대기한다. 이미 준비된 변경안을 최종 적용할 때 다시 생성하는 동작은 추가하지 않는다.

## 후속 구현 전 정할 것

- 초기·유입 Skill 내용, 실제 쟁점 2개, 각 Suggestion 및 시연할 Intent.
- 각 선택이 만드는 정확한 변경 효과와 재검사 응답.
- 개인화 지침, 동일한 질문에 대한 개인화 전후 답변과 근거.
- 캐시 준비·저장 방식, 입력 식별 방식, 초기화·반복 시연 방식.
- Sync의 입출력 방향·충돌 처리, 외부 프로그램과 마켓플레이스의 연동 방식.

구현 후에는 최초 검사 → 선택/Intent → 재검사 → 저장 → Query → 개인화 → Query를 실제 터미널에서 검증한다. 같은 입력의 반복 재생, KEEP 선택, 캐시 누락 입력, 실제 저장된 내용과 Query 근거의 일치, 외부 LLM 호출 없이 끝나는지도 확인한다. 지금은 이 검증을 수행했다는 의미가 아니다.
